# The Evolution of Eldritch: Why We Built a DSL for Realm

If you’ve ever managed a complex red team engagement, you know that maintaining consistency requires discipline and lots of communication. Different operators write scripts in different styles, tools behave differently across operating systems, and “it worked on my machine” becomes the team motto.

When we built Realm, we made a specific choice: we decided against relying on the operating system's native shell. We built a dedicated Domain Specific Language (DSL) called Eldritch. And now, with the release of Eldritch v2, we are doubling down on that decision.

Here is why we put a language inside our C2, and why v2 changes the game.

Why put a DSL in a C2 framework?
The short answer? Consistency.

## Automation: Escaping the Bash Trap
Let's be real: Bash one-liners are a pain when the underlying environment is a moving target. You write a script to grab a payload, but the tools change depending on where you land. Some distros ship with `curl` others only `wget`. Some use `bash` others `ash` or `fish`.

Bash one-liners are annoying because the underlying environment is a moving target. By using a DSL like Eldritch, the agent (Imix) handles the abstraction. You write one command `file.read` and the agent figures out the implementation details for the OS it is running on. You script the intent, not the plumbing.

## TTPs as Code
Treating Tactics, Techniques, and Procedures (TTPs) as code allows operators to move faster and with more confidence during operations.

## Repeatability
Deterministic Actions: Eldritch ensures that persistence is done in a repeatable way each time ensuring steps like timestomping aren't missed.

Replayability: Re-running actions on targets is easy allowing collaborative purple team exercises to tune detections.

## Version Tracking
When your capabilities are defined in code, you gain the power of Git. You can visualize how your tradecraft evolves over time.

What persistence mechanisms have defenders keyed in on?

Which recon commands are firing detections?

This "self-documenting" nature means a new operator can read the code and understand exactly what the team is doing, rather than building long run books that require maintance.

# Why a v2?
Eldritch v1 was based on the Starlark standard (used by Bazel). While Starlark is excellent for build systems, it enforces constraints that make sense for builds but fight against the nature of offensive operations.

Realm v2 introduces a major overhaul to the language engine to better fit the operator's needs.

1. Smaller Size
The original interpreter carried a lot of weight to support features we didn't need. v2 is leaner. A smaller engine means a smaller agent binary, which translates to:

Less noise on the wire during staging.

A smaller footprint in memory, reducing the surface area for EDR memory scanners.

2. More Control Over Language Features
We moved from a generic implementation to a custom one tailored for C2. This allows us to introduce domain-specific types (like Beacon or Creds) as first-class citizens in the language, rather than hacking them together with dictionaries.

3. Removing Unnecessary Restrictions
Starlark was designed to be hermetic and deterministic, which led to two major annoyances for a C2 agent:

Frozen Objects: In Starlark, once a module is loaded, its values are "frozen" (immutable). This is great for preventing build side-effects, but terrible for an implant that needs to maintain state. In v2, we removed this restriction. You can now update global variables, allowing your scripts to be stateful and dynamic (e.g., keeping a running counter of failed login attempts).

Lack of Infinite Loops: Starlark forbids recursion and unbounded loops to prevent builds from hanging. In C2, "hanging" is often the goal—we want an agent to loop forever, polling for jobs or monitoring a log file. v2 enables infinite loops, allowing you to write long-running monitors and daemons directly in Eldritch without complex workarounds.
